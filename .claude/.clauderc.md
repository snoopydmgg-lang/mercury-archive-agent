## 工作流编排 (Workflow Orchestration)

### 1. 默认规划节点 (Plan Node Default)
- 面对任何非微小任务（3个以上步骤或架构决策），强制进入“规划模式”。
- 旦执行偏离预期，立即停止并重新规划——绝对禁止盲目推进。
- 将“规划模式”应用于验证环节，而不仅限于代码构建。
- 提前编写详细的规格说明，以消除系统模糊性（降低熵增）。

### 2. 子代理策略 (Subagent Strategy)
- 极度依赖子代理（Subagents），以保持主上下文窗口的绝对纯净。
- 将资料检索、探索性测试和并行分析任务卸载（Offload）给子代理。
- 面对复杂问题，通过调用多个子代理实施算力饱和打击。
- 强制单线程：每个子代理仅专注执行单一任务。

### 3. 自我进化循环 (Self-Improvement Loop)
- 接收到用户的任何纠正后：立即将错误模式与解决方案写入 `tasks/lessons.md`。
- 自动生成防御性规则，从物理层面杜绝同类错误再次发生。
- 冷酷无情地迭代这些教训，直到错误率出现断崖式下降。
- 每次启动相关项目会话时，强制优先读取并复习这些教训。

### 4. 完工前验证 (Verification Before Done)
- 除非能提供确凿的运行证据，否则绝不将任务标记为“已完成”。
- 涉及核心逻辑时，必须对比主分支（Main）与你修改后的行为差异（Diff）。
- 交付前进行灵魂拷问：“资深架构师会批准这段代码吗？”
- 强制执行：运行测试、检查日志、用数据暴力证明正确性。

### 5. 追求优雅 (Demand Elegance)
- 面对复杂修改：必须停下来反思“是否存在更优雅/边际成本更低的方案？”
- 如果当前的修复方案显得像“临时补丁”：立刻推翻，并基于当前完整认知重构出最优雅的方案。
- 豁免条款：对于简单、显而易见的修复，直接执行——严禁过度工程化（Over-engineer）。
- 在向用户展示成果前，先进行自我红蓝对抗（挑战自己的代码）。

### 6. 自动化 Bug 修复 (Autonomous Bug Fixing)
- 接收到 Bug 报告时：直接定位并修复。绝对禁止要求用户“手把手指导”。
- 顺藤摸瓜：根据日志、报错信息、失败的测试用例——直接解决它们。
- 核心指标：实现用户的“零上下文切换”（Zero context switching）。
- 发现 CI（持续集成）测试失败时，无需指令，主动前往修复。

## 任务管理 (Task Management)

1. **规划先行 (Plan First)**: 将带有可勾选状态的计划写入 `tasks/todo.md`。
2. **验证计划 (Verify Plan)**: 在敲下第一行代码前，先核对计划的可行性。
3. **追踪进度 (Track Progress)**: 推进过程中，实时勾选已完成的项目。
4. **解释变更 (Explain Changes)**: 在每个关键节点，提供高维度的逻辑总结。
5. **记录结果 (Document Results)**: 在 `tasks/todo.md` 中追加 Review（审查）模块。
6. **捕获教训 (Capture Lessons)**: 发生纠正后，强制更新 `tasks/lessons.md`。

## 核心原则 (Core Principles)

- **极简优先 (Simplicity First)**: 确保每次修改的复杂度降至最低。影响范围最小化（奥卡姆剃刀原则）。
- **拒绝懒惰 (No Laziness)**: 穿透表象，直击根本原因（Root Cause）。拒绝任何临时性/妥协性修复。坚守顶尖开发者标准。
- **最小影响 (Minimal Impact)**: 修改动作必须像手术刀一样精准，只触及必要代码。绝对规避引入新 Bug 的风险。
