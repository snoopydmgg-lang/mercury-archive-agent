# 抖音创作 LLM Wiki 知识库规则

## 使用场景

- **用途**：抖音内容创作账号运营
- **素材来源**：GetNote 笔记（抖音视频链接、选题截图、竞品分析）
- **读取方式**：通过 MCP 直接读取 GetNote 笔记

---

## 文件夹结构

```
03_Assets_全局库/
├── raw/                         # 原始素材（只读不修改）
│   ├── AI学习/

│   ├── 账号运营/
│   ├── 选题库/
│   ├── 个人视觉系统设计/
│   └── Clippings/

├── index.md                     # 知识库总目录
└── SCHEMA.md                    # 知识库规则
```

## 原始素材规则

**核心原则**：用户放入知识库的文件 → raw/；Wiki 只存放我萃取的摘要文档。

**来源处理流程：**

1. 用户通过抓取工具、GetNote 等放入知识库的文件 → 直接存入 `raw/` 对应分类
2. **文件名格式**：`YYYYMMDD_主题关键词.md`
   - 示例：`20260411_清明节选题灵感.md`
3. `raw/` 文件夹内容**只读**，永远不修改或移动
4. 我从 raw 内容萃取精华 → 生成摘要文档放入 `wiki/`

---

## Wiki 笔记格式

每条 wiki 笔记必须包含以下字段：

```markdown
---
title: 笔记标题
来源: https://...
核心观点:
  -
  -
适用选题方向:
  -
竞品标签: [如果是竞品分析]
关联笔记:
  - [[wiki/文件名]]
录入日期: YYYY-MM-DD
---

## 笔记正文

...
```

### 各字段说明

| 字段 | 说明 |
|------|------|
| `title` | 标题，能一眼看出主题 |
| `来源` | GetNote 原始链接或视频链接 |
| `核心观点` | 3-5条最核心的洞察，每条一句话 |
| `适用选题方向` | 可以做什么方向的内容 |
| `竞品标签` | 竞品分析必填，如"古月安""意公子"等 |
| `关联笔记` | 用 `[[wiki/文件名]]` 格式链接相关笔记 |
| `录入日期` | 格式 `YYYY-MM-DD` |

---

## 分类规则

Wiki 只存放我萃取的摘要文档，按主题分类：

| 分类 | 存放内容 | 命名规则 |
|------|----------|----------|
| `wiki/AI工具谱/` | AI工具评测、订阅方案对比 | `简洁主题名.md` |
| `raw/选题库/` | 用户收集的背景资料（只读） | 原始文件名不动 |
| `raw/账号运营/` | 运营方法原始资料（只读） | 原始文件名不动 |

**禁止把原始文件放进 Wiki。**

---

## Compile（编译）流程

每次处理新笔记时按以下步骤执行：

**第一步：读取 GetNote / 接收用户文件**
- 调用 GetNote MCP 读取最新收藏的笔记，或接收用户放入知识库的文件

**第二步：放入 raw/ 对应分类**
- 用户文件直接存入 `raw/` 对应分类，文件名不动
- 不修改、不移动、不删除

**第三步：生成萃取文档（如有必要）**
- 从 raw 内容提炼关键信息
- 生成简洁命名的摘要文档
- 放入 `wiki/` 对应分类

**第四步：更新 index.md**
- 在 index.md 更新文件结构表
- 按分类列出 wiki 中的萃取文档
- raw 文件不列入 wiki，只在 index.md 的"原始资料"表中列出

**第五步：日志记录**
- 在 index.md 底部 append-only 日志
- 格式：`## [YYYY-MM-DD] 动作 | 描述`

---

## 查询规则

当用户询问选题、竞品、运营问题时：

1. 先读 `index.md` 找到相关笔记
2. 再读对应 wiki 文件获取详细信息
3. 综合多条笔记给出回答
4. 如果发现好答案，将其提炼为新 wiki 笔记加入知识库

---

## 维护规则（Lint）

每月执行一次：

1. 检查 orphan pages（没有被任何笔记引用的页面）
2. 检查过时内容（与新素材矛盾的）
3. 更新 index.md 中的笔记统计数量
4. 补充缺失的关联笔记链接

---

## 去重规则（防止重复导入）

每次执行 compile 前，必须先执行以下检查：

1. 读取 index.md 底部的日志区域，获取所有已导入笔记的标题列表
2. 从 GetNote 获取笔记后，逐条对比标题或来源链接
3. 如果某条笔记的【来源链接】或【标题】已存在于 wiki/ 任意文件中，则跳过，不重复写入
4. 只处理全新的笔记
5. compile 结束后，在日志中注明：本次新增 X 条，跳过重复 X 条

## 来源唯一性原则

- 每条 wiki 笔记的【来源】字段是唯一标识
- 写入新笔记前，先用 grep 搜索 wiki/ 目录下是否已存在相同来源链接
- 如果已存在，则更新原文件而非新建

---

## 物理架构规范（空间拓扑 × 时间序列）

| 文件 | 职责 | 性质 |
|------|------|------|
| `index.md` | 知识库总目录、空间拓扑、Wiki 页面索引 | Append-only（修改需格式化） |
| `log.md` | 操作日志时间序列 | Append-only（仅追加） |
| `raw/` | 原始资料（只读） | 物理隔离，不修改 |
| `wiki/` | 萃取文档（实体页/概念页/对比页） | 拓扑节点，可增不可删 |

**index.md 与 log.md 严格物理隔离**，不得混合存储。

---

## Wiki 页面拓扑规范（网状交叉引用）

**页面类型**：
- **实体页** — 具体对象（AI模型、产品、人物）
- **概念页** — 抽象概念（RAG、思维链、复利）
- **对比页** — 多维对比分析（工具选型、方案对比）

**强制引用规则**：
- 新建 Wiki 页面时，必须扫描 `index.md` 中所有现有页面
- 使用 `[[页面名称]]` 或相对路径建立与现有页面的交叉引用
- 每个页面至少有一条出站链接

---

## Query 流程与 Write-back 闭环

**标准 Query 流程**：

1. 读取 `index.md` 定位相关 wiki 页面
2. 读取对应 wiki 实体/概念/对比页
3. 综合多条笔记给出回答
4. 若回答涉及多维对比或深度推演 → 触发 Write-back

**Write-back 触发条件**（满足任一）：
- 复杂查询（跨3个以上 wiki 页面的综合分析）
- 高价值对比（工具选型、方案决策）
- 原创推演（非直接摘取，产生新洞察）

**Write-back 执行步骤**：
1. 将推演结果沉淀为独立 Wiki 页面
2. 命名格式：`wiki/对比分析/YYYYMMDD_主题.md` 或 `wiki/概念/YYYYMMDD_概念名.md`
3. 在页面内使用 `[[交叉引用]]` 连接相关现有页面
4. 追加 `log.md` 日志条目：`## [YYYY-MM-DD] query-writeback | 页面名称`
5. **不更新 index.md**（保持 index.md 为静态索引）
