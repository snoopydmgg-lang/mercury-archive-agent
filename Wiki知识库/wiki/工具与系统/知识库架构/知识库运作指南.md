## 核心理念

**知识是创作的副产品，而非目的。**

知识库不是用来"收藏"的，是用来"调用"的。每一条信息进入知识库，都应该有一个明确的用途方向——选题参考、文案借鉴、工具选型、或认知升级。

### Karpathy LLM-Wiki 范式革命

**核心突破**：将 AI 从"搜索引擎"重新定位为"知识工程师"，实现知识的**持续增量构建与维护**。

**三大核心理念**：
1. **从检索到编译** — 不是每次查询都重新检索，而是让 AI 主动整理知识形成结构化 Wiki
2. **知识复利增长** — 每次摄入、每次提问都持续丰富知识库，形成"使用即增值"的良性循环
3. **零维护成本** — AI 承担全部维护工作（交叉引用、摘要同步、矛盾标注），人类只负责摄入和思考

**与传统 RAG 的本质区别**：

| 维度 | 传统 RAG | LLM-Wiki（Karpathy 方法） |
|------|---------|--------------------------|
| **工作模式** | 无状态检索（每次从零开始） | 有状态编译（持续积累） |
| **知识沉淀** | 提问即忘，知识不关联 | 一次编译，持续复用 |
| **适用规模** | 企业级海量数据 | 个人/中小团队（几十万字） |
| **核心目标** | 如何高效找出信息 | 如何持续整理好知识 |
| **维护成本** | 需人工管理向量库 | AI 自动维护，零人工成本 |

**三条铁律：**
1. **RAW 只读** — 原始文件一旦进入 `raw/`，永不修改、永不移动、永不删除
2. **Wiki 只存萃取** — Wiki 文档是我从 RAW 内容提炼的精华，不是原始文件
3. **AI 自动化** — 让 AI 代替你做整理工作，你只负责摄入和思考

## 物理架构（三层架构设计）

### Karpathy 三层架构（标准范式）

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：Raw Sources（原始资料层）                            │
│  - 论文、文章、图片、数据文件                                 │
│  - 权限：LLM 只读，不可修改                                   │
│  - 作用：知识源头，不可变存储                                 │
├─────────────────────────────────────────────────────────────┤
│  第二层：The Wiki（知识编译层）                               │
│  - 结构化 Markdown 文件集合                                   │
│  - 内容：摘要、实体页面、概念页面、对比分析、综述             │
│  - 权限：LLM 可写，用户可读                                   │
│  - 作用：知识沉淀主体，动态更新的知识网络                     │
├─────────────────────────────────────────────────────────────┤
│  第三层：The Schema（规则配置层）                             │
│  - 规则文件（如 CLAUDE.md、SCHEMA.md）                        │
│  - 权限：人工定义，LLM 遵循                                   │
│  - 作用：指导 Wiki 组织方式与约定                             │
└─────────────────────────────────────────────────────────────┘
```

### 本项目实现（四文件隔离）

```
┌─────────────────────────────────────────┐
│  index.md   — 空间拓扑（目录索引）       │  ← 静态，不混日志
│  log.md     — 时间序列（Append-only）    │  ← 仅追加，不混目录
│  raw/       — 原始资料层（只读物理隔离） │  ← 对应 Raw Sources
│  wiki/      — 萃取文档（网状拓扑）       │  ← 对应 The Wiki
└─────────────────────────────────────────┘
```

**严格物理隔离原则**：
- `index.md` 不得混入 `log.md` 内容
- `log.md` 仅作时间流水，格式：`## [YYYY-MM-DD] Action | Target`
- Wiki 页面之间通过双链语法建立网状引用
- Raw 层绝对只读，Wiki 层由 AI 自动维护

**核心价值公式**：
> **Obsidian = IDE，LLM = 程序员，Wiki = 代码库**
> 
> 解决人类维护知识库的痛点：自动处理交叉引用更新、摘要同步、矛盾标注等琐碎工作，将维护成本降至接近零

| 类型 | 定义 | 示例 |
|------|------|------|
| **实体页** | 具体对象 | Claude、GPT-SoVITS、飞书 |
| **概念页** | 抽象概念 | RAG、思维链、复利 |
| **对比页** | 多维对比分析 | AI成本控制方案、工具选型对比 |

### 强制引用规则

- 新建 Wiki 页面时，**必须**扫描 `index.md` 中所有现有页面
- 使用双链语法建立与现有页面的交叉引用
- 每个页面**至少有一条出站链接**
- 禁止创建孤立页面（无任何页面指向它）

### 3. Graphify（知识图谱编译器）

**核心价值**：将任意文件夹一次性编译成可查询的知识图谱，实现 **70倍以上的 token 压缩**。

**解决的痛点**：
- 传统 AI 编程助手处理整个项目时需重新读取数万至十几万行代码，导致响应缓慢、成本高昂
- AI 在大量文件中易丢失上下文，难以把握项目全局结构

**技术架构**：
- **确定性路径**：依赖 Tree-sitter 进行静态 AST 解析，精准提取函数/类调用关系
- **概率性路径**：由 LLM 并行提取语义处理、文档、决策逻辑等非结构化信息
- **双轨策略**：确保图谱既有精准的结构化关系，又有丰富的语义信息

**完整工作流水线**：
1. **Detect** — 识别文件类型
2. **Ingest** — 排队入库
3. **跨文件解析** — Build 整合成图
4. **Cluster** — 执行社区检测，自动划分代码模块
5. **Analyse** — 负责架构关系计算
6. **Report** — 生成 Markdown 报告
7. **Export** — 交付可用图谱

**核心输出文件**：

| 文件名 | 作用 |
|--------|------|
| `graphify_graph_report.md` | 知识摘要，汇总项目架构全貌 |
| `graph.html` | 图谱可视化看板（网页格式） |
| `graph.json` | 图谱原始数据源，支持自定义查询 |
| `cache/` | 增量编译核心，仅处理变动代码 |

**适用场景**：
- 代码库分析（定位模块调用链与数据流）
- 大型项目架构理解
- 多模态输入支持（代码、PDF、截图、录音）

**核心功能**：
1. **微信集成** — 支持微信扫码登录，覆盖私聊、群聊双模式，兼容图像、视频、文件、语音

| 层级 | 核心内容 | 访问权限 | 核心作用 |

| **Agent 拥有层** | 摘要、实体概念、综述、导航文件（index）、交叉引用 | 大模型创建更新 | 知识结构化呈现 |

**基础操作流程**：
1. **技能调用**：在终端输入 `/llm-wiki` 命令启动功能

5. **多库管理**：支持创建多个独立 Wiki，并可无缝切换

**与 Graphify 的差异**：

| 维度 | Graphify | Hermes Agent LLM Wiki |
|------|----------|----------------------|
| **处理对象** | 项目文件（代码库） | 日常笔记、论文等文档 |
| **核心功能** | 构建代码的确定性逻辑 | 维护知识的语义关系 |
| **构建方式** | 静态扫描 + 自动监听更新 | 动态追踪 + AI 摘要提炼 |

## Compile 流程（Karpathy 四阶段）

### 三大核心操作（LLM-Wiki 标准）

#### 1. Ingest（录入）
- 用户添加新文件至 Raw Sources 层
- LLM 自动读取资料 → 提取关键信息 → 生成摘要页 → 更新索引 → 联动更新相关实体/概念页面
- **关键特性**：单个来源可牵动 **10-15 个 Wiki 页面**更新

#### 2. Query（提问）
- 用户向 Wiki 提问，LLM 搜索相关页面综合回答
- **知识复利**：优质回答可回存为 Wiki 新页面，实现"提问即知识积累"

#### 3. Link（体检）
- LLM 定期检查 Wiki 健康度：识别页面矛盾、过时信息、孤儿页面
- **主动进化**：主动建议新研究方向，推动知识网络自我优化

---

### 阶段1：Ingest（摄入）

**工具**：Web Clipper / extract-getnote-articles / 手动放入

**操作**：
1. 使用 Web Clipper 保存网页到 `raw/` 对应分类
2. 或在 Claudian 中执行：`/ingest https://example.com/article`
3. 或手动将文件放入 `raw/` 对应分类

**原则**：
- 文件名保持不变（或使用 `YYYYMMDD_主题.md` 格式）
- 只读不动，永不修改

---

### 阶段2：Compile（编译）

**触发方式**：在 Claudian 中执行 `/compile`

**AI 自动执行**：
1. 扫描 `raw/` 中所有未编译的资料
2. 为每篇生成摘要 → `wiki/summaries/`（可选）
3. 提取概念 → `wiki/concepts/`（可选）
4. 提取实体 → `wiki/entities/`（可选）
5. 更新索引 → `index.md`
6. 建立交叉链接（使用 `[[双链语法]]`）
7. 追加 `log.md`

**判断是否需要萃取**：
- 包含可复用的方法论或原则 → 萃取
- 包含对比分析或决策依据 → 萃取
- 包含背景信息（下次会用到）→ 萃取
- 纯原始数据（CSV、截图、图片）→ 不萃取

**编译策略（大模型时代）**：

| 维度 | 策略 |
|------|------|
| **实体层** | 采用粗粒度定义（如 person/organization/product），避免过度细分 |
| **关系层** | 半开放策略：不预定义关系类型，优先使用原文动词或自然语言描述 |
| **演进机制** | 后期通过标签（tag）细化实体分类，通过模型批量合并相似关系 |

---

### 阶段3：Query（查询）

**标准查询流程**：
1. 读取 `index.md` 定位相关 wiki 页面
2. 读取对应 wiki 文件
3. 综合多条笔记给出回答
4. 若产生新洞察 → 触发 Write-back

**在 Claudian 中使用**：
```
@wiki/indexes/All-Concepts.md
请帮我总结关于"XX主题"的所有资料，
并找出不同笔记之间的关联。
```

**多跳查询限制**（重要）：
- **推荐跳数**：2-3 度关系可解决大部分关联问题
- **风险警告**：无限制多跳查询会导致指数级数据爆炸和语义漂移
- **正确做法**：超过 3 度关系需拆分为子问题

---

### 阶段4：Lint（维护）

**触发方式**：在 Claudian 中执行 `/lint`

**AI 自动检查**：
1. 找出不一致的信息
2. 补充缺失的交叉链接
3. 建议新的研究方向
4. 标记过时的内容（`[OUTDATED]`）

## 高效学习方法论（输出驱动）

### 核心思维模型

**学习的本质规律**：
- **核心公式**：**输入≠学习，输出=学习；重复≠进步，纠错=进步**
- **关键机制**：学得快的人本质是在**更短时间内完成更多次高质量反馈循环**
- **认知真相**：未经检验的理解几乎都是错觉，大脑通过"碰壁"而非"观摩"获得成长

### 低效学习的典型陷阱

#### 假学习行为表现
1. **形式化输入**：将"看过"当"学会"、"理解"当"掌握"、"准备"当"行动"
2. **囤积式学习**：大量看书、记笔记、收藏课程、做思维导图，却缺乏实际应用
3. **完美主义拖延**：追求一次性学透（"等准备到九十分才开始"），导致永远停留在起点

#### 多任务陷阱
- **贪多求全**：同时学习表达、拍摄、运营等多领域技能，导致认知负荷超载
- **低效循环**：看似忙碌却无实质产出

### 高效学习的实践框架

#### 核心行动原则

| 原则 | 具体做法 | 效果 |
|------|---------|------|
| **快速下场** | 刚学一点就讲给别人听，刚懂框架就解决问题 | 提前进入"会用-敢用-被反馈-再修正"循环 |
| **高频反馈** | 每天针对性训练，即时回看纠错 | 20天内完播率提升，内容产出效率翻倍 |
| **压缩链路** | 学完立刻用，想到立刻测，做完立刻复盘 | 减少"知道到做到"的时间差 |

#### 单点突破策略
- **聚焦主能力**：一个阶段只抓一项核心技能，围绕其高频练习
- **阶梯式掌握**：先构建 70 分粗框架，再通过实践补细节、修动作、形成直觉

### 关键执行细节

#### 基建原则（每次学习必做三件事）
1. **用自己的话复述**：确保"真懂"而非"看懂"
2. **即时场景应用**：哪怕成果粗糙，也要落地实践
3. **聚焦单一修正点**：复盘后只改最关键的问题，避免贪多

#### 心态调整
- **放下自尊心**：接受"前期难看"的现实，高手的光鲜是"打磨几百次"的结果
- **用行动换反馈**：将"怕丢脸"转化为"主动暴露不足"

## CloudCode 配置体系（双层级架构）

### 核心架构

**双层级七文件**结构，实现全局与项目的精细化管理：

| 层级 | 文件数量 | 生效范围 | 核心功能 |
|------|---------|---------|---------|
| **系统层级** | 3个 | 全局生效（所有会话） | 定义基础身份、权限与规则 |
| **项目层级** | 4个 | 当前项目生效 | 存储项目专属记忆与配置 |

### 系统层级配置

#### 1. claude.md
- **核心定位**：AI 的"身份说明书"，定义用户基本信息与工作方式
- **关键内容示例**：
  - 身份描述："我是独立开发者"
  - 技术栈：常用开发工具与技术框架
  - 工作准则：
    - **先研究再动手**：要求 AI 优先调研 GitHub 等平台现有工具
    - **关键节点确认**：重要步骤需用户确认后执行
    - **最小编辑面**：明确工作风格与需求边界

#### 2. settings.json
- **核心定位**：权限控制与环境管理中心
- **三大功能模块**：
  - **工具权限**：可开启 bypass 模式，无需重复确认
  - **钩子系统**：定义工作流触发规则
  - **环境变量**：存储 API 密钥、模型参数等敏感配置

#### 3. rules
- **核心定位**：代码编码规范与安全规则的强制执行文件

### 项目层级配置

#### 1. 项目专属 claude.md
- **核心定位**：项目背景与工作方式的详细说明
- **应用场景**：
  - 亚马逊选品项目：记录选品方向、策略与注意事项
  - 短视频项目：定义内容风格、创作方向与已有题材延续规则

#### 2. memory.md
- **核心定位**：项目专属记忆库（系统层级无此文件）
- **关键作用**：
  - 自动加载历史交互记录
  - 保存产品信息、选品规则等项目数据
  - 支持跨会话内容延续与关联

#### 3. commands
- **核心定位**：项目专属命令集，优化特定场景操作效率

#### 4. settings
- **核心定位**：项目级别的配置项，覆盖系统层级未包含的个性化需求

### 配置实施路径
1. **基础构建**：先完成系统层级配置，确立全局规则
2. **项目适配**：针对不同项目配置专属文件
3. **协同生效**：系统配置 + 项目配置 = **项目专属 AI 助理**

## 知识图谱构建方法论

### 核心价值与应用场景

**核心解决问题**：解决**信息碎片化**问题，通过实体与关系的结构化聚合，实现跨片段的关联查询。

### 使用误区与风险

#### 典型错误用法
1. **无限制多跳查询**
   - 盲目使用多跳查询会导致**指数级数据爆炸**
   - 造成 CPU/内存资源耗尽

2. **语义漂移风险**
   - 过度关联会产生无意义关系，导致模型输出**事实幻觉**

#### 正确使用原则
- **多跳限制**：**2-3 度关系**可解决大部分关联问题，超过则需拆分子问题
- **关系聚焦**：优先提取直接关联的实体关系，避免无意义链路

### 构建方法论

#### 传统构建方式：顶层设计（本体设计）
- **核心流程**：预先定义实体类型和关系类型，严格限制抽取范围
- **优势**：结构规范，关系明确
- **问题**：工程繁重，需 5 年以上才能落地应用

#### 大模型时代构建方式

| 维度 | 策略 |
|------|------|
| **实体层** | 采用粗粒度定义（如 person/organization/product），避免过度细分 |
| **关系层** | 半开放策略：不预定义关系类型，优先使用原文动词或自然语言描述 |
| **演进机制** | 后期通过标签（tag）细化实体分类，通过模型批量合并相似关系 |

### 工程落地关键考量

#### 技术选型与工具
- **推荐框架**：**LightRAG**（当前最优解决方案）
- **核心提示词设计**：需明确实体提取规范，确保模型输出符合预期

#### ROI 评估：二八法则
- **常规场景**：80%-90% 的检索问题可通过优化切片 + 向量库双路召回解决，无需图谱
- **高价值场景**：法律、药物研发、科学探索等领域，图谱构建 ROI 显著
