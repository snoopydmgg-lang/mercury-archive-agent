# Graphify 知识图谱工具使用指南

> 把代码项目变成知识地图，70 倍 Token 压缩，让 AI 不用每次都重新读代码

---

## 核心痛点与解决方案

### 传统 AI 编程助手的局限

**三大问题**：
1. **效率问题**：处理整个项目时需重新读取数万至十几万行代码，导致**响应缓慢**
2. **成本问题**：大量代码读取消耗**大量 Token**，增加使用成本
3. **方向迷失**：AI 在大量文件中易丢失上下文，难以把握项目全局结构

---

### Graphify 的解决方案

**核心思路**：
- 将任意文件夹一次性编译成可查询的**知识图谱**
- AI 后续查询仅需读取图谱结构，无需访问原始文件
- 官方宣称实现**七十倍以上的 Token 压缩**

**效果对比**：
- 传统方式：10 万字代码 → AI 每次都要读 10 万字
- Graphify：10 万字代码 → 编译成 1400 字图谱 → AI 只需读 1400 字

---

## 产品定位与核心功能

### 产品本质

**CLI 工具 + Agent Skill 的组合体**，通过简单命令即可集成到 AI 助手。

---

### 四大核心功能

| 功能 | 具体描述 | 对水星艺术馆的价值 |
|------|---------|------------------|
| **70倍 Token 压缩** | 原始需处理 10 万字代码，压缩后仅需 1400 字 | 省钱、提速，管理 Python 脚本更高效 |
| **多模态输入支持** | 处理代码、PDF、截图、录音等多种格式 | Wiki 笔记、文案文档都能入图 |
| **自动更新机制** | 代码修改后实时同步图谱，无需手动重跑 | 脚本改了自动更新，不用手动维护 |
| **完全本地运行** | 零数据库依赖，确保数据隐私绝对安全 | 数据不上传，隐私安全 |

## 技术架构与工作流程

### 图谱生成策略

**确定性 + 概率性双轨策略**：

1. **确定性路径**
   - 依赖 tracet 进行静态 AST（抽象语法树）解析
   - 精准提取函数/类调用关系
   - 示例：`generate_copywriter.py` 调用 `getnote_api.py`

2. **概率性路径**
   - 由 LM（语言模型）并行提取语义处理、文档、决策逻辑等非结构化信息
   - 示例：分析文案生成的业务逻辑

---

### 完整工作流水线

**7 步流程**：

1. **Detect**：识别文件类型（Python、Markdown、PDF 等）
2. **Ingest**：排队入库
3. **跨文件解析**：Build 整合成图
4. **Cluster**：执行社区检测，自动划分代码模块
5. **Analyse**：负责架构关系计算
6. **Report**：生成 Markdown 报告
7. **Export**：交付可用图谱

**多模态处理**：
- 音频：通过本地 Whisper 模型转录
- 视觉内容：调用多模态识别能力
- 统一入图

## 输出文件说明

### 核心输出文件

| 文件名 | 作用 | 用途 |
|--------|------|------|
| `graphifier_graph_report.md` | 知识摘要，汇总项目架构全貌、核心节点关系及关键决策 | 快速了解项目结构 |
| `graph.html` | 图谱可视化看板（网页格式），直观展示代码库网状结构 | 可视化查看项目依赖关系 |
| `graph.json` | 图谱原始数据源，存储完整图结构信息，支持自定义查询或数据库导入 | AI 查询用 |
| `cash` 文件夹 | 增量编译核心，存储上一次扫描结果，仅处理变动代码 | 加速后续编译 |
| `cost.json` | 账单记录，统计调用 LM 进行语义提取的资源/Token 消耗 | 成本分析 |
| `manifest.json` | 图谱配置清单，记录处理文件数、时间戳、配置模式等元数据 | 元数据管理 |

## 质量控制与技术特性

### 质信度分级

**三级可信度**：

| 级别 | 说明 | 示例 |
|------|------|------|
| **Extracted** | 明确定义的源码关系，属于客观事实 | `function A() calls function B()` |
| **Inferred** | 通过语义推导的逻辑，属于合理推论 | "这个函数可能用于数据处理" |
| **Ambiguous** | 无法完全确定的连接，高亮提示人工审核 | "这两个模块可能有关联" |

---

### 底层保障

- 采用标准的 **nodes + edges 骨架**结构
- 通过 `validate.py` 进行完整性校验，确保图谱逻辑闭环

## 水星艺术馆应用场景

### 场景一：管理 Python 脚本

**现状**：
- `06_Python Scripts/` 下有几十个脚本
- 不知道哪个脚本调用哪个模块
- 修改一个脚本，不知道会影响哪些其他脚本

**Graphify 应用**：
1. 对 `06_Python Scripts/` 运行 Graphify
2. 生成脚本依赖关系图
3. AI 能快速定位"配音生成用的是哪个脚本"
4. 修改脚本时，AI 能提示"这个改动会影响 3 个其他脚本"

---

### 场景二：管理 Wiki 知识库

**现状**：
- `Wiki知识库/` 有几百篇笔记
- 不知道哪些笔记相关
- AI 每次都要重新读一遍所有笔记

**Graphify 应用**：
1. 对 `Wiki知识库/` 运行 Graphify
2. 把所有笔记变成知识图谱
3. AI 能快速找到"选品方法论相关的所有笔记"
4. 自动发现笔记之间的关联

**注意**：你已经有 Obsidian 的链接系统了，这个场景可能不太需要。

---

### 场景三：管理文案项目

**现状**：
- `01_Projects_制作中/` 下每个产品的文案、素材
- 不知道哪些产品用了相同的 BGM
- 不知道哪些文案风格相似

**Graphify 应用**：
1. 对 `01_Projects_制作中/` 运行 Graphify
2. 分析哪些产品用了相同的 BGM
3. 哪些文案风格相似
4. 快速定位"版式之道用的是哪套文案模板"

**注意**：文案项目文件结构简单，可能不太需要。

## 与 Graph Memory 的对比

| 维度 | Graphify | Graph Memory |
|------|---------|-------------|
| **处理对象** | 项目文件 | 对话历史与决策日志 |
| **解决问题** | 全局视野受限和冗余 Token 消耗 | 记忆断层和个性化缺失 |
| **核心功能** | 构建代码的确定性逻辑 | 维护对话历史、踩坑记录 |
| **数据源** | 代码、文档、多模态输入 | 对话历史、用户偏好、决策日志 |
| **构建方式** | 静态扫描 + 自动监听更新 | 动态追踪 + AI 摘要提炼 |
| **技术栈** | AST + 图谱可视化 | 向量数据 + 知识图谱 |
| **应用场景** | 定位模块调用链与数据流 | 调取历史决策与排错记录 |

**简单说**：
- **Graphify**：管理代码项目，分析代码结构
- **Graph Memory**：管理对话历史，记录决策和教训

## 是否值得用？

### 优点
- ✅ 大幅提升 AI 处理大项目的效率
- ✅ 省 Token 成本（70 倍压缩）
- ✅ 可视化项目结构
- ✅ 自动更新，不用手动维护

### 缺点
- ❌ 需要先"编译"项目（第一次慢）
- ❌ 适合代码项目，对纯文档项目效果一般
- ❌ 学习成本（需要了解如何使用）

---

### 建议

**适合用 Graphify 的场景**：
- ✅ `06_Python Scripts/`（脚本多、依赖复杂）
- ✅ 大型代码项目（几千行以上）
- ✅ 需要频繁修改代码的项目

**不太需要 Graphify 的场景**：
- ❌ `Wiki知识库/`（已经有 Obsidian 的链接系统）
- ❌ 文案项目（文件结构简单）
- ❌ 小型脚本（几百行以内）

## 使用方法

### 安装

```bash
# 安装 Graphify CLI
npm install -g graphify-cli

# 或者通过 Claude Code Skill 安装
/graphify
```

---

### 基础用法

```bash
# 对项目运行 Graphify
graphify /path/to/project

# 生成输出文件
# - graphifier_graph_report.md
# - graph.html
# - graph.json
```

---

### 查看结果

1. **打开 graph.html**：可视化查看项目结构
2. **阅读 graphifier_graph_report.md**：快速了解项目架构
3. **AI 查询 graph.json**：让 AI 分析项目依赖关系
